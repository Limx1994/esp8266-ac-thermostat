# ESP-12F 空调温控

本工程使用 ESP8266 RTOS SDK 3.4，实现两组温度规则、红外学习与发送及手机配置页。GPIO4 接 DS18B20，GPIO5 接 HS0038B，GPIO14 驱动红外 LED；S1/GPIO12 控制配置热点，S2/GPIO13 关闭热点并进入自动休眠，继续定时温控。项目使用单手机配置，不涉及多客户端。

当前本地版本为 **0.1H（2026-10-06）**。发布内容、产物和验证见 [本地发布](#本地发布)，历史变更通过 `git log` 查询。接线见 [硬件说明](ESP-12F硬件引脚与链路说明.md)，开发约定见 [CLAUDE.md](CLAUDE.md) 和 [AGENTS.md](AGENTS.md)。

## 手机配置

1. 按 S1 开启热点，连接开放 Wi-Fi `空调智能温控`。未自动弹页时访问 `http://192.168.4.1`。
2. 设置两组规则的触发温度（−10～50 °C）、升温或降温方向，保存规则。
3. 点击对应组的“学习红外”，在 15 秒内按一次遥控器目标按键；学习成功后先用“测试发送”验证，再启用并保存规则。
4. 两组共用红外发送频率（36/38/40 kHz，默认 38 kHz）。修改后保存到 NVS，并影响所有已学习编码的后续发送。HS0038B 不能测出遥控器载波频率，需用目标空调验证兼容性。

学习码写入并提交 NVS 后，会读回逐字节核对；核对失败不显示学习成功，当前内存中的旧编码保留，但已提交的 Flash 内容需重新学习确认。学习成功、开机加载及发送完成日志均记录 `code=` 内容校验值，同一组可据此对比重启或休眠前后是否变化。启动时缺失或无效的 NVS 编码会明确记录。默认 `python flash.py` 分段烧录不覆盖 NVS；整片烧录 `full_flash.bin` 或擦除 Flash 会清除保存的数据。编码仍在但空调无响应时，还需核对学习波形及实际发射。

## 电池电压

电压随测温采集，使用 `adc_read` 单次读取，按 330 kΩ / 82 kΩ 分压换算；返回值超出 0～1023 时报错，不额外开启 RF。页面每 2 秒刷新、显示两位小数，刷新不增加采样频率。

进入过自动休眠等待后，热点关闭时临时乘以 **101/111**（约 0.90991），依据历史开机与唤醒 ADC 计数 808/888；首次采样、热点开启及未启用自动休眠时不补偿。日志保留 `adc`、补偿前电压 `measured` 和 `compensated` 标记。页面和低电量判断使用补偿后电压：低于 3.5 V 提示，达到 3.5 V 隐藏；读取失败显示错误，不影响温控。补偿只是临时措施，偏差根因和精度仍未确认。

## 运行行为

| 状态 | 测温与控制 | 指示灯 |
| --- | --- | --- |
| 开机、热点关闭 | 开机立即测温，之后每 30 秒测温并检查规则 | 熄灭 |
| 热点开启 | 每 2 秒测温并检查规则 | 每秒亮 500 ms |
| S2 休眠温控 | 关闭热点，每 30 秒测温并检查规则，间隔允许自动 light sleep | 熄灭 |

S1 可提前关闭热点；红外学习或发送期间将关闭请求延后到红外空闲，再按 S1 可取消待处理请求。休眠中 S1、S2 均通过 GPIO 唤醒：S1 开关 Wi-Fi 热点，S2 快速关闭热点并返回休眠温控。S2 关闭热点后继续每 30 秒采温和按规则发送红外；重复按 S2 不暂停温控、不清空规则状态，S1 可重新开启热点。红外忙碌时，S2 关闭请求延后到空闲；关闭失败会上报错误，温控继续，但不能保证进入休眠。DS18B20 转换期间的按键需等待约 750 ms 加一个 FreeRTOS tick 后处理；长按只产生一次操作。热点关闭失败会记录错误，保留状态供再次操作。

热点开启后，未访问控制页或操作配置 API 时，3 分钟后关闭；使用后从最后一次上述操作起空闲 10 分钟关闭，自动回到休眠温控。状态轮询、系统探测及后台请求不延长期限；红外忙碌时延后关闭。

每次有效采温直接判断启用的规则：升温方向在温度大于等于阈值时满足，降温方向在温度小于等于阈值时满足；首次满足立即发送，无需先跨越阈值。持续满足时，每组距离上次成功自动发送至少 120 秒才再次发送，按下一次有效采样执行；两组独立计时，S2、正常休眠、修改规则及测温错误不清空发送间隔。条件不满足、规则未启用、未学习红外或正在学习时不自动发送；测温失败仅阻止本次发送，恢复有效读数后重新判断。自动发送失败不计入成功间隔，后续采样可重试；网页测试发送不受此自动间隔限制。30 秒采样可能漏掉两次采样之间的短暂越界，也可能使重复发送晚于 120 秒。

## 红外与诊断

红外学习按 10 μs 单位保存完整解调时序，最多 960 段、总时长不超过 750 ms。捕获使用 `esp_timer_get_time()` 计时，保存尾部空闲段；超限、无效波形或保存失败均报错，保留旧编码。学习流程及 NVS 格式保持兼容，无需重新学习；AP 开启时使用 I2S WS + FRC1，AP 关闭时使用 GPIO14 软件载波。清理失败会报错并阻止自动休眠。

DS18B20 的复位和逐位读写使用 RTOS 临界区保护。关键时隙函数放在 IRAM，直接读写 GPIO4 寄存器，按固定 160 MHz 的 CPU 计数器等待各边沿和采样点，避免临界区内的 GPIO API 和 Flash 延时函数带来缓存等待。读位在起始后约 13 μs 采样；计数器差值支持回绕。临界区不覆盖 750 ms 转换等待，也不在其中输出日志；CRC 失败仍报错，不采用旧温度代替有效读数。主机模拟与链接检查不能代替实际 1-Wire 波形和休眠后测温验证。

发送取得忙碌标志和独立休眠锁后，根据 `portal_is_on()` 固定本次路径，日志标记 `backend=i2s/software`。发送前输出编码校验值、恢复 GPIO14 推挽输出并等待 UART 发完；帧内不输出诊断日志。AP 开启路径保留原有 I2S WS + FRC1，不使用 DMA，也不通过 `GPIO_IN` 回读作为发送成功门槛。

AP 开启路径通过 SDK 已链接的 `rom_i2c_readReg_Mask` / `rom_i2c_writeReg_Mask` 保存、使能并读回音频时钟位，仅操作 block `0x67`、host `4`、register `4` 的 bit `7`；定义依据为 [ESP8266 Arduino 的 I2S_CLK_ENABLE](https://github.com/esp8266/Arduino/blob/master/cores/esp8266/esp8266_peri.h)。`audio clock: before=... enabled=...` 记录保存值及使能后读回值；使能验证失败明确报错。停止 I2S 后恢复原值；停止或恢复失败保留原值及休眠锁，后续重试成功再释放。已有未清理的 I2S 状态不能通过软件路径绕过。

AP 关闭路径直接跳过音频时钟读写、I2S 配置和启动，不先尝试使能再回退，也不调用 `phy_open_rf()` 或开启热点。先停止 FRC1、将 GPIO14 拉低，再在整帧 RTOS 临界区内按保存的包络输出软件载波。关键函数及调用链在 IRAM，直接写 GPIO 寄存器，按固定 160 MHz 的 `ccount` 累计截止时间计时；周期为 `round(160000000 / frequency_hz)`，高电平占约半周期，支持 36/38/40 kHz。末尾不完整载波周期在包络截止时截断。保留现有段长和总长范围，最长 750 ms 内普通 RTOS 中断及按键处理会延后；NMI 看门狗保持启用。

软件发送记录 `late_cycles`，为边沿或包络结束相对截止时间的最大迟到 CPU 周期数；160 周期为 1 μs。超过 800 周期（5 μs）时立即拉低输出并返回 `ESP_ERR_TIMEOUT`，不计入成功发送间隔，后续有效采样可重试。5 μs 是软件故障检测阈值，不代表实测精度。发送结束或失败均退出临界区、拉低输出并停止 FRC1；只有整帧完成且清理成功才返回 `ESP_OK`。FRC1 ISR 在软件路径不操作包络或 GPIO mux。

历史实机日志将 AP 关闭后的失败定位到 `stage=clock-enable`：音频时钟置位后读回仍为 0，实际包络为 `segments=0/140`。底层时钟为何不能恢复尚未确认；软件路径绕过该阻断，用户已于 2026-10-06 确认实机验收成功。两条路径均保留 `esp_sleep_lock()` / `esp_sleep_unlock()` 独立保护，清理失败保留锁，后续清理成功释放，避免重复加锁；RF 生命周期、测温、ADC 补偿和每组至少 120 秒的自动成功发送间隔保持现状。

最近一次发送的返回值、路径、阶段、包络完成段数、最大迟到周期数及 I2S 时钟状态留在 RAM，下次采样前通过 `previous send` / `previous clock` 输出。`seq` 为发送序号；多次发送只保留最近一次，断电或复位不保留。软件路径输出 `previous clock: not used`，时钟字段内部为 `-1`，不冒充使能或恢复成功。`stage=envelope result=ESP_ERR_TIMEOUT` 在软件路径表示时序迟到，在 I2S 路径表示等待包络完成超时；清理错误另列。`carrier configured` 和 `software carrier configured` 中的 `calculated` 均为配置计算频率，不是实测频率。`send complete` 或 `ESP_OK segments=140/140` 只代表发送流程及清理完成，不能证明空调已接收。

主机测试覆盖实际源码的 GPIO 边沿、三种载波配置、整帧包络、750 ms 边界、计数器回绕、模拟 NMI 延迟、清理失败重试、NVS 编码保存及两组 120 秒间隔；模拟结果和链接检查不能证明硬件输出准确。实机验收以空调实际响应为准，用户已确认软件载波验收成功；该反馈不等同于所有遥控协议及三种载波配置均已验证。

## 休眠与供电

正常测温间隔和 S2 休眠温控使用 SDK 自动 light sleep，定时唤醒采温及发送红外，完成后继续休眠。热点关闭期间通过 SDK 的 `phy_close_rf()` 关闭 RF，包括测温和红外处理时；开启热点前通过 `phy_open_rf()` 恢复 RF。热点开启、1-Wire 通信、红外学习或发送期间保持 CPU 唤醒。每次测温先检测 DS18B20 供电：独立供电、热点关闭且红外空闲时，GPIO4 切为输入，由板上 4.7 kΩ 上拉维持 DQ 高电平，转换等待允许休眠；读取前关闭自动休眠并恢复开漏输出。RF 开关流程已纳入主机测试，实际电流和休眠唤醒后的 RF 状态仍需实机验证。

转换等待保持 750 ms，并额外等待一个 tick 防止提前读取；不改变传感器分辨率。寄生供电时输出一次警告，保持唤醒等待，不提供强上拉支持。主任务每段阻塞等待最多 10 秒，用于限制 SDK 计时补偿范围，不改变测温周期；实际睡眠时长由 SDK 调度器决定。休眠配置失败后尝试关闭自动休眠并继续温控；若已启用的休眠无法关闭，则中止运行并报错。

本项目使用 LIR2450 锂电池，容量约 120 mAh。电池端功耗测量、按键和连续运行验收见 [功耗验收](tests/功耗验收.md)。当前节电比例与续航尚未确认。

## 构建与烧录

在仓库根目录使用 PowerShell：

```powershell
python build.py
python flash.py --port COM3 --dry-run
```

构建脚本扫描 `main` 源文件，临时映射空闲的 `Z:`，使用 CMake 和 Ninja `-j 12`，产物位于 `build\auto\`。SDK 可通过 `IDF_PATH` 覆盖，工具路径见 [编译环境说明](ESP8266编译环境路径.md)。从其他目录运行时使用脚本的绝对路径。

`sdkconfig.defaults` 设置 CPU 160 MHz、晶振与 Flash 各 26 MHz、`CONFIG_PM_ENABLE=y`、HTTP 请求头上限 2048 字节和 URI 上限 1024 字节。已有 `sdkconfig` 不会被 defaults 覆盖，实际参数以构建生成的 `sdkconfig.h` 和 `flasher_args.json` 为准。

项目 `components\esp_http_server` 覆盖 SDK 的路由、解析和 socket 错误处理，其余实现、头文件及 Kconfig 继续使用指定 SDK。末尾 `*` 匹配剩余路径，`/generate_204_*` 探测重定向至控制页，`/mmtls/*` 的 GET/POST 返回 404。不支持的协议起始字节直接关闭连接，以 INFO 记录原因；HTTP 解析失败返回错误并关闭连接，收发错误保留真实 `errno`。

dry-run 只检查布局，不打开串口、不写 Flash。实际接线与烧录命令见 [工具说明](tools/README.md)；分段偏移以本次构建为准。完整 4 MB 镜像的未使用区域填 `0xFF`，整片写入会清除 NVS；保留规则和编码时使用分段烧录。
